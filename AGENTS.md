# Just Convert — Правила и инструкции для AI-агентов

## 1. Никакого хардкода строк и поддержка i18n

- **Запрещен любой хардкод текста в коде C# и разметке XAML.**
- Любой видимый пользователю текст должен добавляться в словарь `JustConvert.Core.I18n` для обеих культур (`en` и `ru`).
- В **XAML** все строки в рантайме привязываются строго через расширение разметки `{core:Loc Key}` (с пространством `xmlns:core="clr-namespace:JustConvert.Core;assembly=JustConvert.Core"`).
- **Обязательное использование design-time свойств (`d:Content`, `d:Text`, `d:Title`) для предпросмотра в Blend и Visual Studio**:
  В дизайнере XAML (Blend / Visual Studio Designer / WpfSurface) внешние расширения разметки не всегда гарантируют мгновенный рендеринг текста кнопок и надписей. Поэтому каждому элементу с `{core:Loc Key}` **обязательно** задавать соответствующее `d:`-свойство с наглядным текстом на русском языке:
  - Для кнопок: `Content="{core:Loc BtnKey}" d:Content="Текст кнопки"`.
  - Для кнопок со сложным содержимым (`StackPanel` с иконкой и `TextBlock`): указывать `d:Text="Текст кнопки"` у внутреннего `TextBlock`.
  - Для текстовых блоков: `Text="{core:Loc TextKey}" d:Text="Текст надписи"`.
  - Для окон и тайтлбаров: `Title="{core:Loc TitleKey}" d:Title="Заголовок"`.
  - Для условно скрытых элементов (`Visibility="Collapsed"`), которые должны отображаться в предпросмотре дизайнера: задавать `d:Visibility="Visible"`.
  - В блоках `if (DesignerProperties.GetIsInDesignMode(this))` в code-behind окон всегда инициализировать дизайн-состояние кнопок (`BtnPauseAll.Content = ...`), списков и элементов управления.
- В **C#** для получения локализованных строк используется `I18n.T("Key", args)`.

## 2. Чистый код и каскадное удаление неиспользуемого кода

- **Запрещены комментарии в коде**: не добавлять поясняющие или очевидные комментарии в исходный код (C#, XAML и др.). Код должен быть чистым, лаконичным и самодокументируемым.
- **Полное удаление мертвого кода**: запрещено оставлять закомментированные блоки кода, неиспользуемые методы и пустые файлы.
- **Каскадная очистка при удалении или изменении функционала**:
  При удалении любого формата или фичи синхронно удаляются все следы:
  1. Реализация конвертера и его регистрация в `ConverterRegistry.cs`.
  2. Ассоциации типов файлов в `ClassicContextMenuManager.cs`.
  3. Соответствующие неиспользуемые ключи из `I18n.cs`.
  4. Элементы интерфейса из XAML и code-behind.
- Минимализм зависимостей: не подключать сторонние библиотеки, если задачу можно решить встроенными средствами .NET или уже имеющимся FFmpeg.

## 3. Форматирование и переносы строк (CRLF)

- Файлы исходного кода (`.cs`), разметки (`.xaml`), проектов (`.csproj`, `.props`, `.slnx`), конфигураций (`.json`) и документации (`.md`) должны иметь окончания строк **CRLF**.
- Поддерживать актуальность и соблюдать правила [`.gitattributes`](.gitattributes).
- Следовать чистому стилю C# (file-scoped namespaces, явная поддержка nullability, краткие pattern matching).

## 4. Интерфейс и Windows 11 Fluent Design

- Название приложения строго **"Just Convert"**.
- Использовать **WPF-UI** с эффектом Mica (`WindowBackdropType="Mica"`, `ExtendsContentIntoTitleBar="True"`).
- Тема оформления и системный акцентный цвет синхронизируются с системой через `ApplicationThemeManager.ApplySystemTheme()`, `ApplicationAccentColorManager.ApplySystemAccent()`, `ApplicationThemeManager.Apply(this)` и `SystemThemeWatcher.Watch(this)`.
- **Использовать системный акцентный цвет вместо синего**: для интерактивных элементов, прогресс-баров и акцентов использовать системные кисти (`AccentFillColorDefaultBrush`, `AccentTextFillColorPrimaryBrush`), избегая статичного дефолтного синего цвета.
- **Фиксированный размер окон**: запрещено позволять изменять размер окон пользователем (`ResizeMode="NoResize"`, фиксированные `MinWidth`/`MaxWidth`, `MinHeight`/`MaxHeight`, `ShowMaximize="False"`).
- Не использовать тяжелые фоновые карточки/плашки вокруг базовых элементов управления (радиокнопки, чекбоксы), сохраняя нативный стиль Windows 11.

## 5. Документация и README.md

- **Запрещено изменять `README.md` без прямого запроса или разрешения пользователя.**
- **Обязательное ведение документации в каталоге `docs/`**: поддерживать актуальность файлов в директории `docs/` по мере добавления, изменения или удаления функционала. Вся техническая документация, описания форматов, аппаратного ускорения, CLI и архитектурных решений должны своевременно фиксироваться в `docs/`.

## 6. Коммиты и правила фиксации

1. **Один логический блок изменений = один атомарный коммит.**
2. **Не выполнять `git add`, `git commit`, `rebase` и другие шаги фиксации без отдельного явного подтверждения пользователя.**
3. **Предлагать план коммитов и порядок только при явном запросе пользователя.** Не засорять вывод предложениями о создании коммитов по умолчанию.
4. **Не пихать все правки и файлы в один коммит разом**, если они логически разделяются. Разделять их строго по смыслу.
5. **Временные `.bak`/backup-файлы** использовать только для безопасного поэтапного разделения правок внутри одного файла; не добавлять их в коммит и удалять сразу после завершения.
6. **При плане коммитов опираться на историю действий**: путь файла, логический блок, цель правки, рекомендуемый commit message.
7. **Формат сообщения коммита**: `<type>(<scope>): <результат на русском языке без точки на конце>`.
8. **Категорически запрещено использовать прямые имена файлов, расширения, классы, методы и переменные в сообщении коммита**:
   - ❌ *Неправильно*: `feat(ui): добавлен TouchpadScrollHelper.cs`
   - ✔️ *Правильно*: `feat(ui): реализована плавная адаптивная прокрутка для тачпадов`
   - ❌ *Неправильно*: `fix(core): исправлен VideoConverter.cs и флаг LastVideoCodec`
   - ✔️ *Правильно*: `feat(core): добавлено запоминание выбранного видеокодека`
9. **Subject формулируется строго в прошедшем пассивном залоге (в форме достигнутого результата)**: `добавлен`, `добавлено`, `исправлено`, `обновлено`, `удалено`, `вынесено`, `настроено`, `переведено`, `оптимизировано`.
10. **Перед commit показать `git diff --staged --name-only`** и кратко перечислить, что коммитится.
11. **Запрещено использовать флаг `--no-verify`**. Если hook падает, исправить замечания и повторить commit без обхода hooks.
12. **Разрешенные типы (`type`)**:
    - `feat` — добавление новой функциональности
    - `fix` — исправление ошибки
    - `refactor` — рефакторинг кода без изменения логики
    - `format` — автоформатирование кода (отступы, скобки, переносы строк)
    - `docs` — изменения в документации
    - `chore` — рутинные задачи, конфиги, скрипты, сборка, хуки
    - `test` — добавление или изменение тестов
    - `revert` — откат предыдущего коммита
13. **Разрешенные области (`scope`)**:
    - `ui` — графический интерфейс (WPF, XAML, стили, окна, анимации, контролы)
    - `cli` — интерфейс командной строки (флаги, параметры, парсинг аргументов, headless-режим)
    - `core` — ядро (конвертеры, probe, кодеки, сканирование, профили)
    - `installer` — установщик и удаление приложения
    - `i18n` — локализация и переводы (ru/en)
    - `config` — проектные конфигурации (.editorconfig, gitattributes, хуки, vscode)
    - `docs` — документация
    - `tests` — общая тестовая инфраструктура и раннеры
14. **Для точечных правок в уже созданных, но не отправленных коммитах**, использовать `git commit --fixup <commit_hash>`, чтобы затем объединить их через rebase с автосквошем.

Короткий шаблон плана коммита:

- `Файл: <путь>`
- `---`
- `Коммит: <type>(<scope>): <сообщение>`
- `Изменения: <кратко>`
